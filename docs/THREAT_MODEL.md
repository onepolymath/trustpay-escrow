# Threat model

TrustPay is an escrow: the only thing that matters is **who can make the vault's tokens move, and where to**. This document lists the actors, what each one might try, and the exact check that stops it. Every row in the table maps to a test in [`packages/sdk/test/integration/program.test.ts`](../packages/sdk/test/integration/program.test.ts) (LiteSVM, running the compiled program).

> Status: hackathon-stage, **unaudited**, devnet only.

## Assets

| Asset                        | Where it lives                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| Escrowed payment             | SPL token account owned by the order PDA (`ATA(order, mint)`). No private key exists for it. |
| Vendor reputation            | `VendorProfile` PDA `["vendor", vendor]`. Only the program writes it, only on settlement.    |
| Arbiter role / window bounds | `Config` PDA `["config"]`.                                                                   |

## Actors and trust

| Actor                     | Trusted for                                    | Not trusted for                                                                               |
| ------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Buyer                     | Their own money                                | Anything about the vendor's money or reputation                                               |
| Vendor                    | Shipping                                       | Holding the buyer's money, or their own reputation                                            |
| Arbiter                   | Deciding the split of a **disputed** order     | Sending funds anywhere else, touching undisputed orders, or ruling on orders they're party to |
| Admin (upgrade authority) | Setting arbiter and window bounds              | Moving any escrowed funds                                                                     |
| Anyone (crank)            | Triggering an auto-release that is already due | Anything else                                                                                 |

## Attacks and mitigations

| #   | Attack                                                                       | Mitigation                                                                                                                                                                                                                                              | Test                                                                         |
| --- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1   | **Vendor takes payment and never ships** (the core Instagram scam)           | Funds sit in the order PDA's vault, not with the vendor. After `ship_by` the buyer calls `reclaim_unshipped` for a full refund; the vendor gets a `missed_shipments` strike, weighted ×2 in the trust score. The buyer can also dispute while `Funded`. | `pay-first-no-delivery protection`                                           |
| 2   | Vendor marks shipped after the deadline to block a refund                    | `mark_shipped` requires `now <= ship_by` (`ShipDeadlinePassed`).                                                                                                                                                                                        | `pay-first-no-delivery protection`                                           |
| 3   | **Buyer receives goods and never confirms**                                  | After shipping, the confirm window starts. Once `release_after` passes, anyone can crank `auto_release` to pay the vendor.                                                                                                                              | `happy path: pay → ship → confirm`, `automatic release and the timeout race` |
| 4   | Race: buyer disputes and vendor auto-releases in the same slot               | `can_dispute` (`now < release_after`) and `can_auto_release` (`now >= release_after`) are exact complements, so only one is ever valid.                                                                                                                 | `automatic release and the timeout race`                                     |
| 5   | Arbiter (or anyone) redirects funds to their own wallet                      | Payout accounts are constrained to `associated_token(order.mint, order.buyer)` and `(…, order.vendor)`. No instruction takes a free destination.                                                                                                        | `disputes and arbitration`                                                   |
| 6   | Arbiter rules on a dispute they're part of                                   | `resolve_dispute` rejects if `arbiter == buyer or vendor` (`ArbiterConflict`).                                                                                                                                                                          | `disputes and arbitration`                                                   |
| 7   | Arbiter rules on an undisputed order                                         | `resolve_dispute` requires `status == Disputed`.                                                                                                                                                                                                        | `disputes and arbitration`                                                   |
| 8   | Non-arbiter resolves a dispute                                               | `has_one`-style check against `config.arbiter`.                                                                                                                                                                                                         | `disputes and arbitration`                                                   |
| 9   | Double release / double refund                                               | Every settle path requires a non-terminal status and sets a terminal one, and the vault is closed in the same instruction. A replay fails on status (and on the missing vault).                                                                         | `double-spend and replay protection`                                         |
| 10  | Wrong mint / fake token                                                      | Vault and payout ATAs are derived from `order.mint`; the mint is fixed when the order is created.                                                                                                                                                       | `funding guards`                                                             |
| 11  | Buyer pays a different amount                                                | `fund_order` transfers exactly `order.amount` via `transfer_checked` (amount + decimals).                                                                                                                                                               | `funding guards`                                                             |
| 12  | Front-running a reserved order                                               | Orders can be reserved for one buyer (`NotReservedBuyer`).                                                                                                                                                                                              | `funding guards`                                                             |
| 13  | Self-dealing to farm reputation                                              | `fund_order` rejects `buyer == vendor` (`SelfDealing`). Sybil buyers are still possible; see the limitations below.                                                                                                                                     | `funding guards`                                                             |
| 14  | Vendor edits their own reputation                                            | `VendorProfile` counters are only written inside settle instructions; there is no setter.                                                                                                                                                               | `vendor registration`                                                        |
| 15  | Config hijack: someone initialises `Config` first with themselves as arbiter | `initialize_config` requires the signer to be the program's **upgrade authority**, checked against the ProgramData account.                                                                                                                             | `config`                                                                     |
| 16  | Admin sets a 1-second window to trap buyers                                  | Windows are bounded by hard limits in code (60 s to 60 days) on top of the configured bounds, and are copied onto each order when it's created, so changing the config later doesn't affect live orders.                                                | `config`, `order creation`                                                   |
| 17  | Stray tokens sent to the vault get stuck, or skew a split                    | Payouts use the vault's **actual balance**, and the vault is closed afterwards.                                                                                                                                                                         | `double-spend and replay protection`                                         |
| 18  | Order id squatting / PDA collision                                           | Order ids are sequential per vendor (`UnexpectedOrderId`); the PDA includes the vendor key.                                                                                                                                                             | `order creation`                                                             |
| 19  | Arithmetic overflow in splits or counters                                    | `u128` intermediate maths for basis points; all counters use `checked_add`.                                                                                                                                                                             | Rust unit tests in `state.rs`                                                |

## Web app

| Risk                                                   | Mitigation                                                                                                                                                                                                                           |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Blink / action endpoint builds a malicious transaction | The action route only builds `fund_order` for the order in the URL, with the payer as buyer. Wallets simulate it before signing. Route params are strictly validated (decimal u64 id, base58 key) and request bodies with zod.       |
| Demo faucet drained                                    | Devnet only (`assertDevnet`), off unless `NEXT_PUBLIC_DEMO=1`, rate-limited per wallet, and only tops up wallets below a threshold. It only ever mints the demo test token.                                                          |
| Demo arbiter key misuse                                | `/api/demo/arbiter` only signs `resolve_dispute` for orders that are already `Disputed`, on devnet, and is disabled unless `NEXT_PUBLIC_DEMO=1`. The key is only an arbiter: by attack #5 it can never move funds outside the order. |
| Burner wallet keys in `localStorage`                   | Clearly labelled as demo wallets, devnet only, and disabled when demo mode is off. Real users connect Phantom, Solflare or Backpack via Wallet Standard.                                                                             |
| Clickjacking / sniffing                                | Security headers in `next.config.ts` (`X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`).                                                                                                                  |

## Known limitations

- **The arbiter is trusted.** A dishonest arbiter can rule unfairly on disputed orders (though only between that order's two parties). Roadmap: a multisig arbiter or a staked juror panel.
- **Sybil reputation.** A vendor can create buyer wallets and run fake orders. Each costs real tokens and fees and is visible on chain, but the program cannot stop it. Roadmap: weight reputation by volume and buyer diversity, and add optional KYC attestations.
- **Off-chain delivery.** The program can't see the parcel. The confirm window plus disputes is the compromise.
- **Unaudited.** Not for mainnet funds.
